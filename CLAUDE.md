# CostCraft — Project Spec for Implementation

A recipe-driven cost and inventory management system for small producer-vendors, designed and validated against a small bakery use case. The JavaEE course design report has been written and submitted as a design document; this file is the **implementation spec**. Build to match.

---

## Context

- **System positioning**: a cost and inventory management tool for small producer-vendors who manufacture goods from raw materials with measurable recipes. Bakery is the primary case study, but the architecture is general (coffee shops, juice bars, soap makers, candle makers, ceramic studios).
- **Primary deployment user**: a real small-bakery operator. Products: Nastar, Kastengle, Putri Salju, Palm Cheese, Crinkle Red Velvet, Chocolate Cashew, Green Tea Almond Cookies, Sandwich Cookies, Pandan Cheese Cookies, Kue Semprit, Chocochips Butter Cookie, Crispy Cheese Almond, Kue Semprit Coklat, Oatmeal Cookies, Lemon Butter Cookies.
- **Replaces**: an existing spreadsheet-based unit-cost calculator, adding overhead allocation across four cost stages, inventory linkage, transactional batch logging, and multi-currency display.
- **Required**: 8 design patterns demonstrated in code.
- **Solo developer, end-of-semester deadline.**

Having the API jars available does not violate the "plain Servlet + JSP + JDBC" architecture as long as the code does not call into them.

## Architecture — Five-Tier MVC

```
JSP (View) → Servlet (Controller) → Service → DAO → MySQL
```

**Strict layer rules**:
- Servlets MUST NOT contain SQL or business logic.
- JSPs MUST NOT contain SQL or business logic. JSTL/EL only.
- Services own transaction boundaries.
- DAOs do CRUD only. DAO methods accept a `Connection` parameter.

### Framework Decision — Hybrid Approach

The 4 committed modules (User & Role, Material & Inventory, Product/BOM/Unit Cost, Production Batch Logging) are built in **plain Servlet + JSP + JDBC**. This is deliberate: it protects Module 4's transactional showpiece (manual JDBC transaction in `BatchService.recordBatch()` — the design's centerpiece, which `@Transactional` would erase) and keeps all 8 design patterns visible as code rather than annotations.

A **Reports module** may be added later as a Spring Boot subproject (stretch goal, not committed). If built, it uses Spring Boot + Thymeleaf to demonstrate framework familiarity alongside the J2EE foundations, and would unlock Template Method as a 9th design pattern via `AbstractReport`. The decision to build Reports is deferred until after the 4 core modules ship.

### Package Structure
```
com.costcraft
├── controller/    # @WebServlet classes
├── service/       # business logic + transactions
│   ├── (MaterialPriceSubject, ProductCostObserver, PriceObserver — Observer)
│   ├── cost/          # UnitCostService's engine: Decorator chain
│   │                  #   (UnitCostCalculation + decorators), Overhead Strategy
│   │                  #   (OverheadAllocationStrategy + impls), OverheadStrategyFactory
│   └── inventory/     # StockMovementCommand + impls (Command)
├── dao/           # JDBC CRUD only; methods take Connection
├── entity/        # POJOs
├── dto/           # transfer objects (UnitCostBreakdown, BatchSummary, etc.)
├── util/          # DBUtil (Singleton), PasswordHasher, MoneyFormatter

```

**Note on pattern placement.** The 8 design patterns are *integrated into the layers they
serve*, not isolated in a `pattern/` package — this keeps the project idiomatic for a Java EE
course (organized by architectural responsibility, not by pattern). Singleton lives in `util/`
(`DBUtil`), Facade in `service/` (`BatchService.recordBatch()`), Observer in `service/`, the
cost-calculation Decorator + Overhead Strategy/Factory in `service/cost/`, the stock-movement
Command set in `service/inventory/`, and the currency Strategy/Factory in `util/money/` beside
`MoneyFormatter`. Template Method (`AbstractReport`) is reserved for the optional Reports module.

## The Four-Stage Cost Methodology

Cost calculation runs in four explicit stages, in this order, never collapsed.

**Stage 1 — Direct Materials.** Sum of `bom_item.gram_quantity × material.unit_cost` for every material in the product's bill of materials.

**Stage 2 — Direct Other Costs.** Physically consumed by the specific batch but not in the BOM:
- Packaging (jar, lid, baking paper, sticker) — fixed per batch or per unit
- Daily-allocated utilities (electricity, water) — monthly amount ÷ days in month × `product.days_per_batch`

**Total Direct Cost = Stage 1 + Stage 2.** This is the base for Stage 3 percentages.

**Stage 3 — Percentage Overhead.** Each applies to Total Direct Cost:
- Operational Cost (default 20%)
- Labor Cost (default 25%)
- Marketing Cost (default 20%)
- Risk Buffer (default 10%)

Defaults total 75% of Total Direct Cost.

**Stage 4 — Unit Cost and Selling Price.**
- Unit Cost = (Total Direct Cost + Total Percentage Overhead) ÷ `product.yield_per_batch`
- Suggested selling price range:
  - Lower = Unit Cost × (1 + `margin_lower_pct`), default 1.30
  - Upper = Unit Cost × (1 + `margin_upper_pct`), default 1.50

**Naming**: Indonesian "HPP" (Harga Pokok Produksi) maps to "Unit Cost". Report uses "Unit Cost (HPP)" once at introduction, then "Unit Cost".

## Multi-Currency — Display-Time Conversion

All monetary values stored in base currency (IDR). User selects display currency; system converts at render time.

**Strategy pattern.** `CurrencyFormatStrategy` interface; implementations per currency handle conversion (via `currency_rate.rate_to_base`) and locale formatting.

**Factory pattern.** `CurrencyStrategyFactory.forCurrency(code)` returns the right Strategy.

**Critical rule**: all money fields render via `MoneyFormatter.format(BigDecimal valueInBase, User user)`. Never render raw decimals.

### Module 4 — Production Batch Logging

The transactionally critical module. Single multi-table write.

`BatchService.recordBatch(productId, multiplier, perMaterialOverrides, workerId, notes)`:

```java
conn.setAutoCommit(false);
try {
    UnitCostBreakdown breakdown = unitCostService.compute(conn, productId);
    BigDecimal unitsProduced = product.yieldPerBatch.multiply(multiplier);
    BigDecimal totalCost = breakdown.unitCost.multiply(unitsProduced);

    long batchId = batchDao.insertBatch(conn, productId, multiplier, unitsProduced,
        breakdown.unitCost, totalCost, workerId, notes);

    for (BomItem bi : bomDao.findByProduct(conn, productId)) {
        BigDecimal qty = override.getOrDefault(bi.id, bi.gramQuantity).multiply(multiplier);
        BigDecimal priceSnap = materialDao.getUnitCost(conn, bi.materialId);
        batchItemDao.insert(conn, batchId, bi.materialId, qty, priceSnap);
        materialDao.deductStock(conn, bi.materialId, qty);
        inventoryLogDao.insert(conn, bi.materialId, qty.negate(), "BATCH_CONSUMPTION",
            "production_batch", batchId, workerId);
        if (materialDao.isBelowThreshold(conn, bi.materialId)) {
            alertDao.create(conn, bi.materialId, "LOW_STOCK");
        }
    }
    conn.commit();
} catch (Exception e) {
    conn.rollback();
    throw new ServiceException("Batch logging failed", e);
} finally {
    conn.setAutoCommit(true);
    conn.close();
}
```

## Design Patterns — 8 Required

### 1. Singleton — `DBUtil`
Single shared HikariCP DataSource. `com.costcraft.util.DBUtil` — private constructor, static `getInstance()`.

### 2. Facade — `BatchService.recordBatch()`
Hides the coordination of BatchDao + BatchItemDao + MaterialDao + InventoryLogDao + AlertDao behind one method.

### 3. Observer — Material price → product unit cost
`MaterialPriceSubject` (in `MaterialService`); `ProductCostObserver` registered per product. `updatePrice()` fires notify; observers recompute cached unit cost if affected.

### 4. Strategy — Overhead allocation rules
Interface: `OverheadAllocationStrategy { BigDecimal allocate(BatchContext ctx); }`.
Implementations:
- `PerBatchFixedStrategy` → returns `fixed_amount`.
- `PerUnitFixedStrategy` → returns `fixed_amount × yield_per_batch`.
- `DailyAllocatedStrategy` → returns `daily_amount / days_per_month × product.days_per_batch`.
- `PercentageOfDirectStrategy` → returns `percentage × totalDirectCost`.

### 5. Strategy (second use) — Currency display
Interface: `CurrencyFormatStrategy { String format(BigDecimal valueInBase); }`.
Implementations: `IndonesianRupiahStrategy`, `USDollarStrategy`, `ChineseYuanStrategy`, `EuroStrategy`. Handle conversion + locale formatting.

Second genuine Strategy use, different interface, different domain (display vs. computation). Counts independently in the design patterns coursework.

### 6. Factory — `OverheadStrategyFactory` + `CurrencyStrategyFactory`
Both build concrete Strategies from enum/code values. Removes scattered switch statements.

### 7. Decorator — Unit cost composition (four stages)
- Component: `UnitCostCalculation { BigDecimal getTotalDirect(); BigDecimal getTotalPercentage(); BigDecimal getUnitCost(); List<CostLine> getBreakdown(); }`.
- Concrete base: `DirectMaterialsCost` (Stage 1).
- Stage 2 decorators (additive): `PerBatchFixedDecorator`, `PerUnitFixedDecorator`, `DailyAllocatedDecorator`.
- Stage 3 decorators (multiplicative): `PercentageOverheadDecorator`.
- `UnitCostFinalizer` divides by `yield_per_batch`.

Two specialization branches (additive vs. multiplicative) sharing one interface — strong story for the design patterns coursework.

### 8. Command — Stock movements
Interface: `StockMovementCommand { void execute(Connection conn); void undo(Connection conn); String describe(); }`.
Implementations: `PurchaseCommand`, `BatchConsumptionCommand`, `AdjustmentCommand`, `WasteCommand`, `InitialStockCommand`.

`undo()` supports "reverse a mistake" for workers.

**Reserve**: Template Method on `AbstractReport` if Reports module is built.

## Critical Implementation Rules

1. **BigDecimal** for money and gram quantities. Construct from String, never double. `HALF_UP` at display only.
2. **Transactions in Services**, never Servlets or DAOs.
3. **Audit log invariant**: every `material.current_stock` change has a matching `inventory_log` row. Route all changes through `InventoryService`.
4. **Historical cost preservation**: `batch_item.unit_cost_snapshot` is the material price at batch recording time. Never reference live `material.unit_cost` for historical reads.
5. **Cached unit cost** is recomputed when (a) material price changes (Observer), (b) `bom_item` changes, (c) active `overhead_config` changes, (d) `yield_per_batch` or `days_per_batch` changes.
6. **All money display via `MoneyFormatter`** which delegates to user's `CurrencyFormatStrategy`.
7. **PreparedStatement** always.
8. **DAO methods accept Connection** as first parameter.
9. **Validate in Service**, not Servlet. Throw `ValidationException`.
10. **Documented limitations**: no CSRF, no MFA, no password complexity, no rate limiting on login.
